## 2026-08-31 - Memory reallocation in numpy simulation loops
**Learning:** Calling `np.concatenate` to manage rolling history buffers in tight simulation loops (like for Generalized IRF trajectories across `H` steps and `M` parallel histories) is a significant bottleneck due to constant reallocation and copying of the whole buffer, even though the arrays are relatively small per iteration. Pre-allocating the full future length works but increases peak memory. Simply slicing and re-assigning inplace (`buf[:, :-1] = buf[:, 1:]` and `buf[:, -1] = y`) gives ~15% speedup vs `np.concatenate` without the overhead and memory jump of full pre-allocation.
**Action:** When shifting time buffers inplace in high-throughput hot loops with Numpy, use slicing and inplace assignment instead of `np.concatenate` to minimize reallocation.

## 2024-05-18 - Replacing iterrows with pandas vectorize ops inside SQLite executemany
**Learning:** `sqlite3.executemany` expects a list of tuples containing standard Python types (`int`, `float`, `str`, `None`). When replacing `df.iterrows()` with vectorized pandas operations like `pd.to_numeric(errors='coerce')` for SQL insertion, you must explicitly convert the resulting Pandas/NumPy types (like `np.float64` or `NaN`) back to native Python types (`float` or `None`). The conversion from `NaN` to `None` must happen, because `sqlite3` does not support natively inserting `np.nan` into SQLite databases. Additionally, boolean masks must account for unparseable strings versus originally null values (e.g. `df["value"].isna() | vals.notna()`) to correctly mirror the logic of standard row iteration.
**Action:** When vectorizing data preparation for `sqlite3.executemany`, use Python list comprehensions on masked pandas series (e.g., `[float(x) if not pd.isna(x) else None for x in valid_vals]`) to ensure correct type coercion before database insertion. Maintain the original error-handling semantics by accurately checking for missing versus coerced data in boolean masks.
